## 利用方式

| 候補 | 用途 | 確認状況 |
|---|---|---|
| DCS標準JTAC / FAC | 標準の無線メニュー・交信で指定した敵Groupへの攻撃を支援する。第一候補 | DCS公式にFACの対象Group指定があり、同梱MOOSEに呼び出しが存在。Hornet / Apacheそれぞれの交信・照射は未確認 |
| MOOSE `DESIGNATE` | F10からの煙・レーザーなど、メニュー主体の目標指示 | 同梱MOOSEにクラスが存在。標準JTACが目的に合わない場合に別途比較する |

標準JTACとDESIGNATEは別の方式。同じ目標に両方を同時使用して試さず、最初は標準JTACだけで確認する。

同梱の `vendor/MOOSE/Moose.lua` で確認した接続口:

- `CONTROLLABLE:TaskFAC_AttackGroup(...)`：指定した敵GroupへのFACタスクを作成する。
- `CONTROLLABLE:EnRouteTaskFAC_EngageGroup(...)`：指定Groupを対象とするen-routeタスクを作成する。
- `CONTROLLABLE:EnRouteTaskFAC(...)`：周辺の敵を選ぶ汎用FACタスクを作成する。
- `DESIGNATE:New(...)`：MOOSEの目標指示管理を作成する。

CAS試験では、担当外の敵を案内しないよう**指定Groupを対象とする方式**を優先する。タスクを作るだけで割り当てが完了するわけではなく、生成したJTACへの設定と、その後の交信確認が必要。

本番 `.miz` のコピーをMission Editorで編集する。既存の敵・Zone・天候などは試験に必要な範囲以外変更しない。

| 提案グループ名 | 陣営 / 国 | 配置するユニット（MEの検索語） | 数 | DCS TypeName |
|---|---|---|---|---|
| `TPL_CAS_JTAC_01` | BLUE / USA | **ATGM HMMWV**（検索語: `HMMWV`） | 1両 | `M1045 HMMWV TOW` |
| `TPL_CAS_FRIENDLY_01` | BLUE / USA | **M113**（APC） | 2両 | `M-113` |

| 同グループ | RED / Russia | **Truck Ural-4320**（Unarmed、検索語: `Ural`） | 1両 | `Ural-375` |

**3グループ・計7両。Staticではなく、通常の地上車両グループとして置く。** MEの日本語表示やカテゴリ接頭辞は異なる場合があるため、太字の車種で探す。グループ内に複数車種を入れ、ユニット名の連番は自動のままでよい。将来のロジックは表示名の接尾辞ではなく、生成実体で対象を管理する。

MEでJTAC / M113を探すカテゴリは `Armor`、M939トラックは `Unarmed`。`M 818` は内部名で、現在の表示名は `Truck M939 Heavy`。ローカルDCSの `MissionEditor/data/scripts/Enc/Tech/M939.txt` で表示名と内部名の対応を確認した（2026-11-06）。

敵の輸送トラックも `Unarmed` で探す。表示名 `Truck Ural-4320` の内部名が `Ural-375`。ローカルDCSの `MissionEditor/data/scripts/Enc/Tech/Ural-4320.txt` で対応を確認した（2026-11-06）。末尾にT / Arm'd / Mobile C2が付く型とは別なので、今回は通常の `Truck Ural-4320` を選ぶ。

略称は、APC = Armored Personnel Carrier（装甲兵員輸送車）、IFV = Infantry Fighting Vehicle（歩兵戦闘車）、ATGM = Anti-Tank Guided Missile（対戦車誘導ミサイル）。今回のM113はAPC、BMP-2はIFV。APCという表示は味方であることの識別ではなく、車両の用途・種類を示す。

JTACはMEの **ATGM HMMWV** を試験候補にする。現在のローカルDCSの日本語・英語表示カタログでは、旧表示名 `ATGM M1045 HMMWV TOW` が `ATGM HMMWV` へ変換されることを確認した（2026-11-06）。`M1045` では見つからない場合があるため、BLUE / USAの地上車両で `HMMWV` を検索し、ATGM型を選ぶ。Scout HMMWVや通常のHummerとは区別し、内部TypeName `M1045 HMMWV TOW` は変更しない。レーザー照射・標準交信の成立はこの環境では未確認。味方のM113は履帯、敵のBMP-2は砲塔などの特徴を照合する練習に使う。敵味方のトラックも含め、車種や熱源だけを陣営判定の根拠にせず、案内された位置・配置・特徴を合わせて確認する。

### 配置の目安

敵部隊の中央を基準点とし、以下を最初の配置案にする。これは相対位置の案であり、実際の地形・見通し・道路に合わせてMEで調整する。

| 対象 | 基準点から東西 | 基準点から南北 | 置き方 |
|---|---|---|---|
| 敵BMP-2 1両目 | 西40 m | 0 m | 建物や道路の近くの開けた場所 |
| 敵BMP-2 2両目 | 東40 m | 0 m | 他車と重ねず、1両ずつ照準できる間隔 |
| 敵Ural-4320 | 0 m | 北60 m | BMP-2と区別して見える位置 |
| 味方M113 1両目 | 西800 m | 南30 m | 道路沿いの停止部隊として配置 |
| 味方M113 2両目 | 西800 m | 北30 m | 同上 |
| 味方M939 | 西850 m | 0 m | 味方装甲車の後方 |
| JTAC M1045 | 西800 m | 北150 m | 味方近傍で、敵3両すべてへの視線が通る位置 |

JTACと敵の間に建物・樹木・尾根を挟まない。最初は平坦な開けた場所で機能を確認し、その後に低い丘や集落の縁へ移す。ブリーフィングの説明例は「味方は道路沿いのM113 2両とトラック1両。敵はその東約800 m、BMP-2 2両とトラック1両」。実際の配置を変更したら、説明も合わせる。

味方と敵の間隔は約800 mを最初の試験案とし、視認性・地形・使用兵器に応じて調整する。この値を安全距離の保証には使わない。JTACを友軍部隊と兼用するかは、基本動作の確認後に決める。

周波数・AM/FM・コールサイン・レーザーコードは試験前に明示し、既存AWACS・給油機などとの重複を確認する。コードは兵器側と一致させる。標準JTACがどの情報・座標形式を実際に案内するかは記録し、Apacheへのデータリンク受信やTSD自動登録を前提にしない。

### ME設定の初回案

| 項目 | 固定配置の動作試験 | 後の動的生成用TPL |
|---|---|---|
| Late Activation | 3グループともOFF。開始時から存在させる | 3グループともON。原本を有効化せず、生成した実体を使う |
| 経路 | 初期地点だけ。移動・周回を設定しない | まず停止設定を継承する |
| Skill | Highを初回案とする | 初回は同じ値 |
| ROE | **全グループWeapon Hold**。味方・JTACが敵を倒したり、敵が味方を先に破壊したりするのを防ぐ | 基本動作の確認後に、敵の反撃を許すか別途決める |
| Disperse under fire | 初回はOFF。攻撃後も配置を追いやすくする | 散開ありのバリエーションは後で試す |
| 不死 / 不可視 | 初回は設定しない | 初回試験では追加しない |
| JTACの対象 | `TPL_CAS_ENEMY_01`を明示指定 | 生成後の敵Groupを明示指定する |

標準JTACの初回設定は、Advanced Waypoint Actionsの `Start Enroute Task → FAC - Engage Group` など、指定Groupを担当するFACタスクを使用する。汎用FACによる周囲の敵の自動選択は最初の試験では使わない。DesignationはLaserを試す。兵器指定はHornet / Apacheの片方だけに限定しない設定から確認する。

通信用の仮案は**133.000 MHz AM、Axeman 1、レーザー1688**。既存周波数・他JTAC・兵器側設定との照合前なので確定値ではない。レーザーコードをMEで指定できるか、交信で何番が案内されるかを確認し、実際の照射コードに兵器側を合わせる。これらは試験設定であり、配置だけで交信や照射が完了するものではない。

Hornetは既存のDynamic Spawnで出撃してTGPとレーザー誘導爆弾、ApacheはTADSとレーザー誘導Hellfireで確認する。武装の固定スロットや追加のSAM / AAA / MANPADSは最初の試験には不要。停止中の車両がIRで十分見えるかも実機で確認し、特定の状態なら必ず明るく映るとは扱わない。

## 試験の進め方

1. **固定配置の標準JTACを試す。** 敵GroupをMEで明示指定し、1機のHornetで交信・目標説明・レーザー誘導攻撃を確認する。
2. **Apacheでも同じ配置を試す。** 使用無線・メニューへの入り方・PLT / CPGの操作・レーザー捕捉を確認する。Hornetと同じ手順で使えるとは決めつけない。
3. **動的生成へ切り替える。** 実際に生成された敵GroupのIDでJTACへタスクを割り当てる。テンプレート原本や以前の任務のIDを指定しない。
4. **複数任務で試す。** JTAC・敵Group・周波数などの分離方法を確認し、他チームの敵を案内しないことを確かめる。
5. **既存の受注・帰還・採点へ接続する。** 基本動作が確認できた方式をCASモジュールとして統合する。

標準JTACで必要な交信・照射が成立しない、または要求する運用に合わない場合に、同じ配置を使ってDESIGNATEを比較する。

### 単独Apache試験の途中結果（2026-11-06）

- 直近 `dcs.log` はDCS 2.9.31.29434でこの試験のTacview記録を開始したことを示す。`Tacview-20261106-185428-DCS-JATAC_TEST.zip.acmi` にはAGM-114Kが3発ある。

- 発射時の敵までの水平距離は概ね1.3 km / 1.2 km / 0.7 km。地上JTACの視線、実際のレーザー照射点、照射の継続、発射条件のどれが原因かは未確定。保存 `.miz` や通常ログ・今回のTacview記録から、レーザースポットの正確な位置は確認できていない。過去の類似不具合報告を現行版の原因と断定しない。

次回の比較案は、JTAC・敵の配置とコードを維持し、自機だけを敵から3～4 km程度へ離して、SAL / NORM / DIRで1発試す。PRIのレーザー捕捉とJTACの照射継続を確認し、着弾・TADS表示を記録する。距離は原因を切り分けるための試験値で、今回の不発原因や命中を保証するものではない。同じ地面へ外れるなら次にJTAC位置だけを変更し、開けた見通しで比較する。

## 本番CASへの接続方針案

- 独立したCASモジュールで敵・味方・JTACの生成と寿命を管理する。MOOSE APIを優先する。
- 既存の `Missions.Acquire` による受注ロック、Mission Teamの参加者固定、共有目標、UCID別の帰還・精算を再利用する。
- 初回案は停止した指定敵3両の破壊を目標とする。満額150・達成後事故90・未達成事故 / Abort 0を基本案とし、誤射の扱いは実装前に決める。
- CAS用Score・保存schemaの追加要否を決め、必要ならmissionとHookを合わせて更新する。現時点で変更しない。
- 味方位置・特徴・敵の目印をブリーフィングに含める。煙の要求が敵用か味方用かを明確にする。
- `Mission Status` は公開済み説明の再表示に限定する。要求して得た追加情報をどこまで保存するかは、統合時に決める。現在の敵残数や未公開の正確な位置を自動追加しない。
- 標準JTACの発話・対象選定が、任務ごとの情報公開範囲と両立するか確認する。独自F10説明と二重に案内しない。
- 多チーム利用時の周波数・コールサイン・レーザーコードの割り当てと解放、JTAC喪失時の任務継続可否を仕様化する。
- Abort・準備失敗・全参加者終了ではJTACも片付ける。削除失敗は既存の再試行方針に合わせる。

本格的な9-line手順の独自再実装、移動する味方、攻撃許可の独自状態管理などは、基本動作の確認後に検討する。標準JTAC自体が出す交信を省略するという意味ではない。

## 動的CASの構成案（2026-11-06）

ここからは、単独ミッションで標準JTACが使えることを前提にした**未実装の設計案**。現在の本番 `.miz` / Lua / Hookは変更しない。

### 1. 1地域を敵・味方・JTACのセットにする

MEに同じ地域番号を持つ3グループを置く。地域01なら、前述の `TPL_CAS_ENEMY_01` / `TPL_CAS_FRIENDLY_01` / `TPL_CAS_JTAC_01`。それぞれ3両 / 3両 / 1両で、全グループをLate Activationにする。試験用 `.miz` にあるAI Apacheや余分な車両は、本番用TPLセットに含めない。

- 座標・向き・車間・見通しはMEで調整し、Luaへ座標を重複定義しない。
- 初版はMEで確認した地点へそのまま生成する。円内へのランダム移動や向きの回転を行わない。JTACの視線と味方との関係を壊さないため。
- 設定には地域IDと3つのグループ名、必要なら表示用の目印の説明だけを持つ。初期の案内点はMEのJTAC先頭車・敵先頭車・味方先頭車から取得し、用途を区別する。
- 同一地域は1任務だけが使う。敵だけでなく味方・JTACも、生成から削除確認まで1セットとして予約する。
- 地域を増やすときは3グループをセットで複製し、地域番号をそろえる。別地域や既存Strike / SEAD / 車列との近接もMEで確認する。CAS内の予約だけでは他カテゴリとの空間的な衝突は防げない。

### 2. 受注と地域の選定

F10に `Task: CAS` を追加し、Hornet / Apacheの対応任務へ登録する。Dynamic Spawn、同一機の人間PLT / CPG、Mission Teamの受注時参加者固定、個別帰還は既存方式を使う。機体名・出撃空港を受注条件にしない。現在のMission Teamは同機種のみなので、HornetとApacheの混成チーム化はこの追加に含めない。

地域の抽選は既存Air Interdictionと同じく「距離で絞る → 近い2地域を固定 → その中の使用可能な1地域を抽選」を初回案とする。受注時の長機実位置から、MEに置いた敵先頭車の位置までを判定する。Luaのテスト用駐機座標を使わない。

距離の仮案はApache 3～13 NM、Hornet 20～100 NM。ただしCAS配置に対する候補数検証前であり、既存車列の距離をCASへ確定適用するものではない。両候補が使用中・不正なら、3番目や別の距離帯へ自動変更せず受注を解除する。

地上からも受注でき、受注時に3グループを生成する案。地上受注で20秒の離陸待ちを追加せず、離陸前に無線・兵器コードを準備できるようにする。

### 3. 無線とレーザーコードを受注前に選べるようにする

HornetのGBUは搭載後に爆弾自体のレーザーコードを変更できない。このため、任務成立後に未知のコードをランダム割り当てする方式は採らない。

初回案はF10のCAS受注操作で**希望するレーザーコードを選ぶ**方式。例として1688 / 1687 / 1686などを用意し、それぞれに既存支援機と重複しない周波数・AM/FM・コールサインの組を設定する。値・枠数は本番の周波数一覧と照合して決める。選択肢は通常メニューのページ上限を守ってサブメニューに置く。

- 地上では受注して案内されたコードを確認後、同じコードの爆弾へ再武装できる。
- 空中では搭載済み爆弾に合うコードを選んで受注する。スクリプトが搭載爆弾の実コードを確実に読めるとは仮定せず、設定の一致は搭乗者が確認する。
- 同一コードを同時に複数のCASへ割り当てない。周波数・コールサイン・コードをまとめて予約し、選んだ枠が埋まっていたら別コードへ自動変更せず通知して終了する。
- 無線枠が足りなければ受注時のWing / UCIDロックを戻し、生成しない。枠数を機体数上限やBLUE全体の任務1件制限に置き換えない。
- 原本のJTACはLate Activationのままとし、未受注のJTACが交信相手として出ないようにする。
- 標準JTACの交信相手一覧・発話はDCS側の管理。Mission Teamへ通知を絞っても、他のBLUEプレイヤーの交信を完全に禁止・秘匿できるとは扱わない。専用の周波数とコールサインで担当を明示する。
- 自機TGPなど、スクリプトが管理しないレーザーとのコード重複は予約で防げない。ブリーフィングで調整する。

### 4. 生成は3グループをまとめて成立させる

受注からの処理順は次のとおり。

1. 搭乗者と機種対応を確認し、`Missions.Acquire` でWing / UCIDロックを取る。
2. 希望する無線・コード枠と地域を予約し、選んだTPLの独立コピーを作る。途中で再抽選しない。
3. コピー内から、元Groupを指すFACタスクを取り除く。汎用FACや別の担当タスクが紛れていたら生成前に拒否する。ROEなど必要な設定は維持する。
4. 敵 → 味方 → JTACの順に、MOOSE `SPAWN:NewFromTemplate` などで複製する。aliasは `DT_CAS_<assignmentID>_ENEMY / FRIENDLY / JTAC` のように役割別とし、原本名を変えない。
5. 生成実体の陣営・車種・数・Group ID / Unit IDを検証し、敵3両と味方・JTACのIDを保存する。生成参照は検証前から保持し、途中失敗でも回収できるようにする。
6. 生成したJTACから敵3両への見通しを、MOOSEのLOS判定で確認する。地形判定の通過だけで全遮蔽物や実際の照射を保証せず、MEの配置確認・DCS試験と合わせる。失敗時に勝手な座標へ移し替えない。
7. 生成した敵Groupを指定するFACタスクをJTACへ設定し、無線・コールサイン・コードも予約した値へ合わせる。
8. 設定処理の成功を確認してACTIVEとし、採点開始・受注通知・ブリーフィングを送る。DCS標準交信の開始は、プレイヤーが無線で行う。

3グループの出現はゲーム内で原子的に同時にはできない。任務の論理上は全生成・担当設定が済んで初めて成立とし、部分生成を成功通知しない。

**重要：元TPLの敵Group IDを引き継がない。** コピーしたFACタスクの `params.groupId` は必ず生成後の敵IDへ置換する。DCSで新しいGroup IDが決まる前に担当タスクを確定しない。

現在同梱の `EnRouteTaskFAC_EngageGroup` は `laserCode` / `visible` を引数に持たない。一方、保存された `JATAC_TEST.miz` のFACタスクには `laserCode = 1688` / `visible = true` がある。したがって、MOOSEのタスク生成結果へ必要なDCSフィールドを明示するか、MEのFACタスクを独立コピーして必要値を差し替える。初回案は後者とし、元の兵器マスクを含めて保存形式を維持する。標準APIの生データを扱う理由をコメントする。

設定値が不正・実体が未登録なら限定した再試行または失敗解除にし、別の敵やコードで続行しない。タスク設定APIの成功を、標準JTAC交信・照射までDCS内で確認できた証拠とはしない。

### 5. 任務の進行と採点

基本状態は `PREPARING → ACTIVE → RTB_PENDING → 終了`。初回は指定敵3両の全滅で目標達成し、各参加者が既存の帰還評価を受ける案とする。準備中は準備通知だけを出す。

- 撃破は生成実体の固定IDと `Observations` で監視する。nil・例外・Group一覧からの欠落を撃破にしない。
- JTACの台詞や「攻撃終了」通知をLuaの目標達成トリガーにしない。**標準JTACは目標指示・交信、訓練Luaは任務・撃破・採点を担当する。**
- レーザー継続誘導のK、LSTで目標受領後に自機測距して発射するL、Hornetのレーザー誘導爆弾を、指定敵の撃破として同じ条件で扱う。
- 初版はJTACとの交信手順や攻撃許可の取得を自動採点しない。標準交信状態を確実に取得できるAPIがあるとは仮定しない。
- 他プレイヤーの指定敵撃破も、既存Air Interdictionと同様に達成へ数える案。撃破者限定に変更する場合は別途仕様化する。
- 150 / 90 / 0、目標共有・各UCID精算、Apacheの人間PLT / CPGは既存方式を再利用する。
- JTAC喪失時は「支援喪失」を通知して自力で継続可能とする案。自動補充や別Groupへの自動交代は初版に入れない。味方車両・JTACの損失やFriendly Fireを任務失敗・減点にするかは未決定。現行の採点で対応済みとは扱わない。

CAS専用成績は `casScore` を追加する案。現在の `Scoring.NextID` は未登録カテゴリを拒否し、保存schema4にもCAS欄がないため、カテゴリ名を渡すだけでは採点できない。実装時はschemaの更新と旧成績の読み込み、mission / Hookの同時更新・再導入を行う。

### 6. ブリーフィングとMission Status

受注者の機種に合わせ、HornetはDDM・分の小数3桁、ApacheはMGRSの東4桁＋北4桁で表示する案。公開本文は初回に整形して保持し、Statusでは再計算しない。

```text
CAS MISSION
FRIENDLY LOCATION: <味方先頭車の位置>
TARGET AREA: <敵先頭車を使う地域の案内点>
FRIENDLIES: 2 M113s and 1 truck.
TARGETS: 2 BMP-2s and 1 truck.
JTAC: <コールサイン> / <周波数・AM/FM> / LASER <選択コード>
OBJECTIVE: Destroy all 3 designated enemy vehicles; then RTB.
Reward per pilot: 150 points.
Registered pilots: <人数>.
```

これは文面案であり、既存メッセージの確定仕様にはまだ追加しない。初回は座標・識別説明と連絡先を渡し、個別車両の精密座標を3つ列挙しない。案内点に追加のランダム誤差は入れない。味方・敵の相対説明を加える場合は、実際のME位置に合わせる。

標準JTACが交信で出す座標・残存目標の説明は、DCS側の別の公開情報として受け入れる案。SEADの秘匿仕様をCASへ流用しない。標準音声をスクリプトで取得・再表示できるとは仮定せず、Mission Statusは自前で公開した本文だけを再表示する。目標達成後は従来どおり座標なしの達成結果・帰還指示へ切り替える。

EPLRSはME設定を維持するが、ONだけで味方位置がHornet / Apacheへ自動表示・TSD登録されることをCASの成立条件にしない。初版はブリーフィングの味方座標・説明を使う。

### 7. 中止・準備失敗・削除

生成物は敵・味方・JTACの全3グループをCASが所有する。全参加者の精算 / 中止後に全部を削除する。1人の帰還や長機喪失だけでは僚機の支援を消さない。

準備失敗では今回作ったGroupだけを回収し、任務のWing / UCIDロックを解除する。部分生成・登録失敗でも固有aliasから追跡する。地域と無線・コード枠は、JTACも含めた消失確認まで解放しない。削除未確認は5秒ごとに再試行し、再受注した別任務へ同じコードや場所を重ねない。

削除中の喪失イベントを目標撃破・味方損失として数えない。`closing` / `cleaning` と固定IDで区別する。予約の解放・callback・イベントはいずれもassignmentを照合し、古いJTACタスクやタイマーが新任務を操作しないようにする。

CASの生成物・途中経過・無線枠は再起動後に復元せず、精算済み成績だけを保存する。

### 8. 実装時の変更箇所と検証

| 変更箇所案 | 責務 |
|---|---|
| `src/cas.lua` | TPLセット検証、地域計画、生成、固定IDの観測、味方・JTAC状態、削除待ち |
| `src/jtac.lua` | 無線・コード枠の予約、保存FACタスクの検証・再設定、標準JTACへの接続。採点や無線音声の自作は行わない |
| `src/config.lua` | 機種別CAS対応・距離、地域名の対応、無線枠、時間・報酬 |
| `src/missions.lua` | CAS地域・無線枠の予約所有者を任務台帳で管理 |
| `src/main.lua` | コード選択付き受注、既存の共有・状態遷移・イベント・終了・Sweepとの接続 |
| `src/scoring.lua` / `score_data.lua` / 保存関連 | CASカテゴリと累計、旧schema移行・保存確認、Hookの更新 |
| `scripts/Build-Mission.ps1` | JTAC → CAS → mainの依存順でbundleへ追加 |
| `docs/CAS.md` / `MESSAGES.md` / `MESSAGE_FLOW.md` / `TESTING.md` など | 実装時に確定仕様・出力・自動検証とDCS確認範囲を記録 |

単独試験後も、動的生成したJTACへ担当を設定できるかは別のDCS試験とする。自動検証では3TPLの陣営・数・Late Activation、原本の不変、実IDへのFAC差し替え、laserCode / visible / 兵器マスク、コード競合、途中生成失敗と削除再試行、別任務の隔離、同一機の複数人・個別帰還、schema移行を確認する。実DCSでは動的JTACの無線メニュー登録、K / L / Hornetでの交信と撃破、LOS、並行JTAC、支援喪失・終了後の残留を確認する。

実装開始前に確定する項目は、CAS地域の配置数・距離・抽選、無線枠の値と数、希望コード選択UI、味方損失 / 誤射の評価、公開メッセージ。今回の整理ではこれらを提案として残し、本番への配置・コード変更は行わない。
