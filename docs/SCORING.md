# プレイヤー採点・帰還評価仕様

更新日: 2026-10-07

現在の採点対象は Intercept / CAP / SEAD / Immediate DEAD / Follow-on DEAD。Intercept は敵航空機全滅、SEAD は主要レーダーの破壊または損傷＋Radar OFF連続60秒、DEADは開始時の残存対象全滅でクリアとする。CAPはzone内累計120秒と敵航空機全滅の両方でクリア。詳細は [CAP.md](CAP.md)。
Immediate DEADは同じSEAD sortie内のphaseとして、SEADのID・達成結果・報酬を維持し、独立したDEAD報酬を追加する。詳細は [DEAD.md](DEAD.md)。
SEAD の対象レーダーと配置の仕様は [SEAD.md](SEAD.md) を参照する。SEAD の採点は模擬テスト済みで、ゲーム内確認は未実施。

## 現在の実装と範囲

マルチプレイの静的 Client スロットを対象とした試用実装。
UCID の照合、グループ別 F10 メニュー、クリア後の帰還評価、100% / 60% / 0%の精算、
重複防止、成績表示とサーバーHookによる永続保存はコードに実装済み。
ユーザーから任務がゲーム内で動作しているとの報告あり。
UCID 取得・着陸・事故イベントの個別ケースの確認範囲は未記録。
サーバー用Hook導入時は保存済み累計をミッション再開始・サーバー再起動後も復元する。未接続時はセッション内のみ。導入・保存状態・復旧は [PERSISTENCE.md](PERSISTENCE.md) を参照する。2026-10-06に初期接続・CAP90点の保存と次セッションへの引継ぎを確認済み。帰還150点の保存、復元成績のStatistics画面などは確認待ち。

設定は [src/config.lua](../src/config.lua) に集約する。
初期の試用値は満額150ポイント、失敗率60%、着陸確認10秒、停止判定5 knots。
Intercept の満額は `intercept.fullReward`、SEAD の満額は `sead.fullReward`、両DEADの満額は `dead.fullReward` で個別に設定する。Interceptは旧トップレベルの`fullReward`から移動し、初期値150は維持する。
CAPの満額は `cap.fullReward`（150）。CAP Scoreへ独立加算し、他カテゴリのScoreへ加算しない。Total/Careerと既存の任務・帰還・喪失統計は共通精算を使う。保存schema2でCAPを追加し、schema1の既存成績はCAP=0として読み込み、従来の累計を維持する。
Difficulty / Threat Budget による配点、追加ボーナス、カテゴリ Rating は未実装。

## 採点規則（実装済み）

| 状況 | 付与額 |
|---|---|
| 任務クリア後、BLUE 飛行場・空母への帰還成功 | 満額の100%（現在150） |
| クリア後、帰還成功の確定前に墜落・死亡・脱出 | 満額の60%（現在90） |
| 未クリアの墜落・死亡・脱出 | 0 |
| 任意 Abort | 0 |
| UCID を取得・照合できない訓練 | 採点なし |

60%の規則は着陸進入中に限定せず、クリア後の帰還途中の事故・被撃墜も対象とする。
60%の付与額は整数に切り捨てる。例えば満額101なら60ポイント。
Intercept/SEADの満額は敵生成成功時、Follow-on DEADは受注時、Immediate DEADはContinue時に固定する。主要目標達成時点では累計へ加算しない。
帰還成功・失敗で確定した額を Total Score、Career Points と、その任務の Intercept Score / CAP Score / SEAD Score / DEAD Score に同額加算する。
各Scoreはカテゴリ別累計であり、Ratingではない。両DEADの満額は `dead.fullReward = 150`。

Immediate DEADは同じRecovery結果でSEADと追加DEAD報酬を別々に精算する。両目標達成＋帰還なら各150で合計300、両目標達成後事故なら各90で180、DEAD未達成事故ならSEAD90＋DEAD0。任意Abortは両方0。
DEAD未達成で安全帰還した場合はSEAD150＋DEAD0。その後の僚機による達成で精算済み報酬を変更しない。
Continue前の精算済み参加者やDEAD達成前の終了者へ追加報酬を遡って与えない。任務数・Primary成功数・Recovery等は元SEADの1件を維持し、追加DEAD精算で二重に数えない。

受注時に同じグループへ搭乗する人間全員への達成報酬。満額は各自150で、編隊人数で分割しない。
目標達成は共有するが、帰還・事故・個人中止・精算は UCID ごとに独立する。
先に帰還した人へ先に加算し、全員の精算または中止まで任務と受注ロックを維持する。
クリア前に死亡・中止した参加者へは、編隊が後でクリアしても報酬を遡って与えない。
編隊共有の詳細は [WING.md](WING.md) を参照する。
AI 僚機や他の味方がその任務の対象を破壊した場合もクリアに含める。
個別の撃墜者・撃墜数による報酬は未実装。

## UCID と要求者の識別（実装済み）

成績は `Scoring.players[ucid]` に保持し、表示名は表示用に記録する。
同じ UCID は名前やスロットを変えても同じ累計を参照し、同名でも UCID が違えば別の成績になる。

F10 メニューはプレイヤーグループごとに生成し、受注時にそのグループの人間プレイヤー全員を登録する。
BLUE / `FA-18C_hornet` が対象。人間が0名のグループでは生成しない。
MP2 の Client ×2、単独 Client、人間1名＋AI 僚機に対応する。空席・AI は参加者に登録しない。
グループ共有の F10 は実行者本人を識別しない。長機の基準は搭乗者の機体番号順で決める。
メニューの作成・削除は接続中の BLUE プレイヤーを2秒間隔で検出して行う。

UCID はサーバー側の接続情報を照合して取得する。
MOOSE の `CLIENT:GetUCID()` はサーバー用 API として定義され、
同梱の取得処理は名前から playerID を検索する。
今回の `player.lua` は同名プレイヤーの取り違えを避けるため、DCS 標準 `net` API で接続情報を列挙し、
表示名・BLUE 陣営・Client のテンプレート `unitId` とネットワークの `slot` が一致する1件を採用する。
DCS 標準 API を使う理由をコードにも記載する。
[MOOSE CLIENT ドキュメント](https://flightcontrol-master.github.io/MOOSE_DOCS/Documentation/Wrapper.Client.html)

UCID は空でない文字列のみ採用する。接続中の playerID は永続成績のキーにしない。
実機でテンプレートの `unitId` とネットワークの `slot` の対応を確認する。
動的 Client スロットや複数乗員のスロット表記は今回の試用対象外。

UCID が取得できない場合は「採点なし」と表示して訓練を継続する。
名前・機体名・仮の UCID を成績のキーに使わない。
途中で UCID が取得できるようになっても、その非採点任務を後から加算しない。
UCID の全文をゲーム内表示や通常のログに出力しない。

任務には開始時の UCID、機体名、DCS オブジェクト ID、DCS オブジェクト参照を保持する。
機体の喪失イベントではこの記録を使うため、死亡・脱出後に UCID がイベントから取得できなくても元の所有者へ精算できる。
同名機体の再スポーンや別スロットの機体を、前の任務の帰還成功として扱わない。
全カテゴリ共通のMOOSE受信者は`DynamicTrainingRuntime.eventHandler`でミッション終了まで保持する。弱参照の登録だけでGCにより死亡・帰還イベントが届かなくなる不具合をtraining-4で修正した。機体ID・元のDCS実体の照合と一度だけの精算規則は維持する。

## 状態と精算（実装済み）

状態は [src/missions.lua](../src/missions.lua) の `Missions.wings[groupName]` とその参加者一覧に集約する。
状態の更新は [src/main.lua](../src/main.lua) が行う。
ウィングごとに同時に1任務で、帰還待ちもその1件に含める。別ウィングは並行して受注できる。
ウィング名と登録 UCID に受注ロックを設定し、1人の精算・スロット変更では解除しない。

Intercept は `ARMED` → `TAKEOFF_DELAY` → `ACTIVE`、SEADは計画作成の `PLANNING` を経て同じ離陸待ちへ進む。
各カテゴリとも主要目標達成後は `RTB_PENDING` → 全員終了で解除、の順に進む。
ImmediateはSEAD達成後に `DEAD_ACTIVE` を挟み、全対象破壊で `RTB_PENDING` に戻る。Continue時の既存着陸確認は解除するが、その後はDEAD未達成でも新しい着地からSEADの帰還を評価する。帰還成功確定時にDEAD未達成ならSEAD150／DEAD0、確定前にDEADも達成していれば各150を精算する。DEAD達成時は進行中の確認を維持し、復行時の戻り先をRTB_PENDINGへ変更する。
DEAD未達成の帰還は個別終了とし、未精算の僚機は戦闘を継続できる。全員終了でIN_USE SiteをCleanupし、精算済み参加者へ後からDEAD報酬を付けない。
Follow-on DEADは地上受注ならARMED、全員離陸でACTIVE。20秒待ち・再Spawnはなく、地上予約の事故・中止は0で精算する。
帰還待ちの各参加者は `RTB_PENDING` → `LANDING_CHECK` → 個別精算へ進む。
Intercept は全員が空中で要求した場合に `ACTIVE` へ即座に進む。
Intercept の地上予約は全参加者の離陸検出から20秒待つ。詳細は [Intercept.md](Intercept.md) を参照する。
SEADの地点選定は地上・空中を問わず開始する。受注時から全員が空中なら計画確定後に生成し、地上受注なら全員の離陸検出から20秒待つ。

敵生成失敗時は採点対象の実行中任務を作らない。
生成後の経路設定に失敗した場合は敵を削除し、再要求を可能にする。

敵は生成時の各 DCS オブジェクトに対応付け、死亡・墜落・喪失イベントで主要目標を判定する。
SEAD は主要レーダーだけを対象とし、発射機が残っていても帰還評価へ進む。完了状態は固定し、残存車両の追加撃破に報酬はない。
残敵は全員終了時に独立したサイト管理がdispositionで処理する。標準CLEANUP、明示保持のみRETAIN、IN_USE終了はCLEANUPへ倒す。削除失敗で精算を巻き戻さず、参照を保持して再試行する。
RETAIN Siteの保持者ログアウトでは精算前でもSiteだけCleanupする。ログアウトやSite削除自体を成功・失敗・Abortとして採点せず、元SEADの達成結果と帰還評価・確定済みポイントを維持する。
1秒間隔の監視でも生存状態を確認するが、未精算の元の参加者機が全機失われた後に遅れてクリアを推測しない。
イベント処理で確認したクリア時刻を保持し、それより前のプレイヤー事故に60%を付与しない。
実際のイベント発火・配信順序はゲーム内で確認が必要。
DCS が必要なイベントを通知しない場合、帰還・事故の精算が保留される可能性がある。

精算記録は `Scoring.settlements[mission.id]["ucid:" .. ucid]` に参加者ごとに一度だけ作る。
Immediate DEADでは元SEAD IDに加えて `record.deadScoringID` の追加精算記録を作る。参加者の `deadScoring` はcategory=DEAD、scoreOnly=trueを持ち、DEAD達成時刻を元SEADと分離する。追加精算は成績累計だけを更新する。
同じ任務IDを共有する2人の精算は互いを上書きしない。
UCID 不明の参加者はセッション内の機体 ID で別の非採点記録を保持し、仮の成績アカウントは作らない。
脱出・墜落・死亡が同じ事故で重複しても、ポイントと各件数の更新は一度だけ。
精算済みの任務への別の結果通知は既存の結果を返し、変更しない。
全員の精算・中止後は任務とロックを解除してからSiteの終了方針を処理し、削除によるイベントを任務クリアと誤認しない。
1人の事故・個人中止だけでは敵を削除せず、残る参加者の任務を継続する。
他のウィングの敵・帰還評価・精算記録には影響しない。任務IDは全ウィングを通じて異なる連番を使用する。
新しい任務IDを発行するので、前の精算記録で次の任務を加算済みと誤認しない。

現在の任務IDはカテゴリ間でも共通の連番。保存接続後はHookが採番したrun番号を含む `run1:Intercept:1`、`run1:SEAD:2` などとし、未接続時は `Intercept:1` のようなセッション内IDを使う。
SEADは受注時にIDを計画へ保存し、生成成功後も同じIDで精算する。計画・生成失敗や生成前の中止には参加者の採点記録を作らない。
精算台帳は現在のミッション内に保持する。保存時は精算済み累計とrun番号・revisionを同じsnapshotに記録し、再送は累計の置換とする。完了した任務を再起動後に再加算しない。

## 帰還成功（実装済み）

以下をすべて満たすこと。

- 任務がクリア済みで未精算。
- 開始時のプレイヤーが同じ機体の同じ DCS オブジェクトを操作している。
- 着陸先が帰還時点で BLUE の飛行場、または対応する BLUE 空母。
- 生存しており、脱出していない。
- 地上状態を維持し、速度5 knots以下を連続10秒維持する。

`EVENTS.RunwayTouch` / `EVENTS.Land` が示す着陸先を接地候補として使用する。
最寄り基地だけを根拠に帰還成功とは認定しない。
飛行場はその場所から水平2,500 m以内、空母は水平350 m以内に留まることを確認する。
空母は接地時の艦との高度差から5 m以内を維持することも確認する。
距離・高度差は初期の判定値で、実機で調整する。

空母では艦の速度ベクトルを差し引いた相対速度を使う。
対応空母の機種は設定に列挙する。現在は Stennis、CVN_71～75、Forrestal。
空港名・艦名はハードコードしない。FARP、野外、敵・中立基地、非対応の艦は帰還成功の対象外。

1秒監視で停止条件の開始時刻を記録するため、10秒維持の確認には最大約1秒の追加検出遅れがある。
同じ場所への重複した着陸イベントは確認タイマーをリセットしない。
再浮上、離陸イベント、判定範囲外への移動、基地の陣営変更では着陸確認を解除する。
速度が5 knotsを超えると連続10秒の計測をやり直す。

エンジン停止、出撃した基地への帰還、ノーダメージは要求しない。
硬着陸・機体損傷だけでは60%にせず、帰還条件を満たせば100%。
復行、バウンド、ボルターは帰還待ちに戻し、再着陸できる。

## 帰還失敗・離脱・中断（実装済み）

`Crash`、`Dead`、`PilotDead`、`Ejection`、`UnitLost` を共通の失敗精算へ渡す。
イベントの DCS オブジェクト参照または ID を照合し、該当する参加者だけを精算する。
AI 僚機・未参加者・別グループのプレイヤーの事故は参加者の精算に使わない。
帰還確認の10秒間に事故が起きた場合も60%。
100%を確定した後の事故では、すでに付与したポイントを減額・再加算しない。

退出・スロット変更だけでは自動的に60%を付与しない。
元の UCID と機体を保持し、帰還待ちを継続する。
元の機体の喪失イベントが確認された場合は、クリア済みかに応じて60%または0%で精算する。
同じ所有者が同じ機体へ戻れば帰還評価を再開できる。退出中の連続停止時間は加算しない。
別スロットへ移っても、現在の UCID を照合して名前・機体を指定する `Abort Sortie` で自分だけを中止できる。
元のウィングの共有 F10 では登録者がいるグループから対象を選んで個人中止できる。
`Abort Mission` は元のウィング全体を中止する。単独任務は同じ UCID の別スロットからでも全体中止できる。
別グループに登録者がいなければ中止できない。F10 はグループ共有で、クリックした本人は識別しない。
任意 Abort は0ポイント。精算済みの参加者の報酬は変更しない。

## F10 の成績表示（実装済み）

`Dynamic Training → Player Statistics` で以下を表示する。
そのグループに現在搭乗する人間全員について、次の項目を25秒間表示する。

- `PLAYER STATISTICS`: プレイヤー名・機体名。
- `Total Score`: 累計スコア。
- `Career Points`: 累計ポイント。現在はTotal Scoreと同額を加算する。
- `Settled Missions`: 精算済み任務数。
- `Primary Success`: 主要目標達成数。
- `RTB Success`: 帰還成功数。
- `Recovery Failure`: 主要目標達成後の帰還失敗数。
- `Death Count`: 墜落・死亡・脱出などによる出撃喪失数。
- 全員分の末尾に保存状態を1回表示する。保存済み／保存待ち／Hook未接続／保存無効／保存エラーを区別する。

Intercept / CAP / SEAD / DEADのカテゴリ別Scoreは画面に表示しない。カテゴリ別の加算・永続保存・復元は継続する。
UCIDを照合できない搭乗者はプレイヤー名と `UCID unavailable; unscored.` を表示し、成績値は表示しない。
通常の画面メッセージと同じ本文をDCSログのMESSAGEへ記録する。表示例は [MESSAGES.md](MESSAGES.md#screen-player-statistics--25-seconds-requested-manually) を参照する。
この表示変更は実装済み、DCS内の画面確認は未実施。

各件数は任務精算時に更新する。主要目標達成から帰還待ちの間は件数も未精算。
`Mission Status` は自分のウィング、または搭乗中 UCID に紐づく元の任務の状態・長機の基準・参加者の個別状態を表示する。生成までの残り秒数はInterceptだけで表示し、SEADはDEBUG限定とする。

## 永続保存（実装済み・DCS内確認待ち）

ミッション側の `src/persistence.lua` とサーバー用Hookへ保存処理を分離する。ミッションのio / lfsをunsanitizeせず、サーバーのSaved Games配下へ固定schemaのデータを保存する。
復元時は既存累計へ未接続期間の精算差分を1回だけ統合する。保存失敗はsnapshotを再送し、ポイントを再加算しない。保存待ちと保存済みはHookの確認通知で区別する。
任務数・Primary成功数・帰還成功／失敗数・未達成失敗数・中止数と、死亡／墜落／脱出／UnitLostによる出撃喪失数 `deathCount` を保存する。Immediate DEADのscoreOnlyでは統計を増やさない。
未精算任務とSAM Siteは復元しない。ファイル検証・backup復旧・導入手順は [PERSISTENCE.md](PERSISTENCE.md) を参照する。

`scripts/Test-All.ps1`で両bundleを結合し、Lua全9スイートとBuild/Sync/Installテストを実行する。個別コマンドと検証範囲は [TESTING.md](TESTING.md)、全体の責務と用語は [ARCHITECTURE.md](ARCHITECTURE.md) を参照する。
結合済みの本番コードを読み込み、DCS / MOOSE の呼び出し先だけを模擬する。
計算、UCID・スロットの照合、名前変更、再スポーン、着陸確認、動く空母、重複事故、Abort、複数任務の累積を自動検証する。
Player Statisticsの表示時間25秒・カテゴリ別Score非表示と、カテゴリ別集計・復元の維持も既存テストで検証する。現在の自動テスト結果は [TESTING.md](TESTING.md)、過去の実測記録は [HISTORY.md](HISTORY.md) を参照する。新表示のDCS内確認は未実施。

実際のマルチプレイでは次を確認する。

1. F10 の `Task: Intercept` で満額150ポイントが表示される（採点なしの場合は UCID / スロット取得を確認）。
2. 敵全滅で帰還指示となり、次の Intercept が抑止される。
3. BLUE 飛行場・空母で停止して帰還確定後、成績に150ポイントを反映する。
4. 別の試行でクリア後に脱出・墜落した場合、90ポイントを一度だけ反映する。
5. 未クリアの事故と任意 Abort は0ポイントで任務を解放する。
6. MP2 の2人に独立して150／90ポイントを付与し、AI 僚機・未参加者の着陸・事故では成績が変わらない。
7. ボルター・復行、退出・再参加、再スポーンした機体の扱いを確認する。
8. Hook導入時は保存済み表示後にミッション再開始・サーバー再起動し、同じUCIDの成績が戻る。Hookなしではセッション内のみの表示で0に戻る。
9. 全員の終了前に同じウィング・登録 UCID が再受注できず、最後の精算・中止でロックを解除する。
10. 長機がクリア前に死亡しても僚機は継続でき、長機0・帰還した僚機150となる。
11. 別ウィングが並行して受注でき、各任務の敵・帰還・中止が他方のポイントやロックに影響しない。
12. SEAD の主要レーダーの破壊、または損傷＋Radar OFF連続60秒で帰還待ちになり、帰還150／事故90が SEAD Score に加算され、Intercept Score が変わらない。

実機確認前の制約: UCID が取得できること、飛行場・空母のイベント発火条件と着地判定、
イベント配信順序、各 Client スロットのメニューの挙動は自動テストだけでは保証しない。
